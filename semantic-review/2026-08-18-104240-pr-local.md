# MMRM 后半流程的 TFL 绑定、审批与收集

改动以 `source_tfl_id` 将 Endpoint Mapping 映射到候选 TFL，并生成每个 TFL 唯一的 contract analysis；`source_ref` 留作来源追溯，不进入 contract identity。运行入口重新校验 approved specification、review hash、签核状态和 execution hash，草稿及审批回滚后的残留产物不能通过正常入口执行。collector 固定 `fail_fast=false`、逐 analysis 收集并将 group 拟合隔离，manifest 按 contract catalog 覆盖每个 TFL。Watch for: **confirmed — case summary 可接纳与当前 contract/manifest 不一致的既有 run record；confirmed — 唯一集成测试只覆盖单 TFL、单 group，未覆盖 `fail_fast=false` 的单 TFL 失败续跑或 partial summary。**

**Verdict**: NEEDS_CHANGES

## High-level view

`source_tfl_id` 是绑定键：生成阶段要求 analysis 与候选 TFL 双向一对一，specification validator 又逐 group 对照 review mapping 和 contract。`source_ref` 被保留为同一 TFL 的来源说明，并非第二个 contract 绑定键。

审批链 fail-closed：draft 只能供签核，wrapper、collector 与 case-summary 均要求 approved specification；审批回滚后，残留 specification 因 review hash/status 不匹配而不可执行。

collector 为每个 contract analysis 创建 manifest 行，即使 wrapper 或 artifact 失败也继续处理后续 TFL。case summary 虽核对 manifest 的 TFL 集合，却未将已存在 run record 重新绑定到当前 contract/manifest，partial 时可能混入陈旧状态或哈希。

## source_tfl_id 的一对一 contract 绑定

`analysis_specification_mapping_tfl_index()` 要求 `source_tfl_id` 存在于第 3 节候选 TFL；同一 `analysis_id` 只能引用一个值，任何 TFL 不能被两个 analysis 引用，且两个集合必须相等。`analysis_specification_contract()` 仅从该索引写入 contract `tfl_id`；`validate_review_contract_endpoint_mapping()` 再逐 `analysis_id/group_id` 比较 review `source_tfl_id` 与 contract `tfl_id`。

`source_ref` 仍是 review 的必填追溯字段，validator 仅确认其中的 TFL 标识与本行 `source_tfl_id` 一致。它不进入 contract schema 或 `analysis_specification_contract()` 的 identity 选择，故不会覆盖 contract TFL。

## draft 与 approved 的执行隔离

wrapper、collector 和 case-summary 都调用 `assert_approved_specification()`，它复核 specification `status=approved`、当前 review hash、`review_status=approved`、最终签核、reviewer/UTC、Endpoint Mapping 与 execution hash。审批脚本若后续 validation 失败会恢复 review；已写出的 specification 因持有临时 review hash 而不能再通过上述 gate。未发现草稿或审批回滚产物的 fail-open 执行路径。

## collector 的失败隔离和 TFL 清单

`standard_resolve_fail_fast()` 固定返回 `FALSE` 并拒绝 true。collector 逐 contract analysis 调用 wrapper；缺 wrapper、非零退出或 terminal artifact 只影响当前 analysis，循环继续。analysis 内各 group 使用独立 `callr` worker，失败 group 形成 `fit_failed` diagnostics，成功 group 保留结果并使 analysis 收敛为 `partial`。manifest 无论 artifact 是否存在都按 catalog 写一行，因此实现上对 contract TFL 完整覆盖。

## partial case summary 的陈旧记录混入风险

`standard_case_summary()` 验证 manifest 的 `tfl_id` 集合、唯一性和行数与 contract catalog 完全相等，再为每个 catalog analysis 建立 record。但已有 `analysis-run-record.csv` 只要恰有一行且有指定列就被采用；它未验证 `contract_sha256` 等于当前 contract，也未将其 `output_status` 与 manifest 同行核对。`validate_standard_case_summary()` 也只比较 catalog 与 run-record 的 `analysis_id` 集合。**confirmed —** contract 更新、旧输出未清理或文件被替换时，summary 可包含当前 catalog/manifest 与旧 run record，partial 的失败状态、风险和 provenance 可能不属于当前 contract。

生成时应校验 `contract_sha256 == attr(contract, "sha256")`，并比对 manifest 同行的状态；更稳妥的是将 `tfl_id` 纳入 summary run-record schema，核对 `(analysis_id, tfl_id, contract_sha256, output_status)`，不合格则生成当前 manifest 状态的 synthesized record。diagnostic metadata 也应只纳入 hash/analysis identity 一致的行。

## 新契约的测试夹具未覆盖主失败路径

`R/tests/check_standard_profile.R` 的合成 contract 只有一个 `analysis_id`、一个 `tfl_id` 和一个 group。它仅验证单例 `source_tfl_id` happy path、`fail_fast=false` 解析、single-wrapper 缺失的 manifest，以及单 analysis case summary。**confirmed —** 它不能发现 collector 提前停止的回归，也不能检验 partial manifest/case summary 对全 contract TFL 的覆盖；没有 stale run record、contract hash 不同或 manifest/record 状态分叉的夹具。

新增 fixture 应含两个 analysis：第一个 terminal failure，第二个有效 artifact；断言两个 manifest rows、第二个 invocation/record 存在、overall 为 partial、summary catalog/run_records 均覆盖全部 TFL，并加入 stale-record rejection 断言。
