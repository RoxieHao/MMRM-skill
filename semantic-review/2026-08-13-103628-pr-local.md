## High-level view

审批链验证 workbook 文件 SHA、spec 第 1–8 节 execution SHA 和完整 spec SHA，但 execution SHA、reviewer、accepted/modified 与 resolved 状态均由 workbook 生成脚本写入。该链能发现单边文件漂移，却不能证明统计师批准字段真正驱动了 spec。

R 和五份 SAS template 都按列存在性选择 `REGION`，仅在不存在时选择 `COUNTRY`，并在批准筛选后少于两个非缺失水平时停止。当前五项产物均为 `COUNTRY`、1 个水平、`blocked_data`、无 covariance/model，raw/final 固定为 17/18 列 header。

Collector 的 run-and-collect 要求本次 invocation，collect-only 要求当前完整 spec SHA；当前 manifest 五行均为 `blocked_data`，summary 为 `failed`，legacy comparison 明确没有 V2 model 或可比 LSMean。单项 diagnostics 和 study summary 使用 `not_assessed`/“未执行”，但单项 Markdown 报告仍把收敛显示为“否”。

## Workbook-backed approval remains self-attested

`build_review_workbook.R:15-16` 从现有 `analysis-specification.md` 计算第 1–8 节 execution SHA；`:34-49` 将该 SHA、`project_user`、审核日期和 `accepted/modified` 写入 `Study概览`，`:116-118`、`:154`、`:174`、`:196`、`:236-237` 又把 mapping/model/TFL/QC 行标成已接受、问题标成 resolved。生成候选规则与代表人工批准是同一个可重复运行的脚本动作。

`specification.R:81-88` 只要求批准值/来源/状态完整，`:138-154` 比较少量 identity 字段并确认 workbook 保存的 SHA 等于当前 spec 第 1–8 节 SHA。它没有从 workbook 的 `批准值` 构造 canonical contract 后与 spec 比较：人工修改批准字段但保留旧 execution SHA 时，字段与执行规格的分歧不会被识别；改动 spec 后重跑 builder，则会生成自动宣称接受新 spec 的 workbook。当前 workbook SHA `73CC…C9616B`、完整 spec SHA `FAD6…0B2C2` 和 execution SHA `5A34…8027` 通过 validator，只能证明文件相互引用一致，不能证明批准来源独立。

修复时应将 extraction workbook 生成与 human approval finalization 分开，以已批准字段生成 canonical execution contract 并比较 digest/spec；`reviewed_by`、`reviewed_at`、状态和 issue resolution 不应由候选生成脚本硬编码。需要防止协调改写时，再把批准 digest 放入独立签名或只读 approval artifact。

## Blocked models are reported as non-converged

`fcn_v2_runtime.R:543-548` 在单水平时于模型前停止，`:660-684` 写出 `blocked_data`、`convergence_status=not_assessed`、空 model path 和固定 schema。报告逻辑 `fcn_v2_runtime.R:435` 却把所有非 converged 情况归为“否”，使五份 `mmrm-run-diagnostic-report.md:14-18` 同时出现“Covariance 执行路径：未执行”“模型是否收敛：否”和“模型未执行，无法评估计算风险”。这会把数据契约阻断误读成优化器未收敛，重新模糊 `blocked_data` 与 `fit_failed`；应优先识别全部 `not_assessed` 并输出“未执行/无法评估”。
